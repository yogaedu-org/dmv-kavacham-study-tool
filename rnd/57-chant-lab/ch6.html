A sound model for Sanskrit

The quick check only compares sound with sound. The deeper check adds a model that knows what speech sounds like, so it can say which sound was heard. Here is what it needs, what it hears, and where it can run.

The candidate

The report recommends ZIPA, a sound model trained on many Indian languages, among them Hindi, Marathi, Bengali, Telugu and Tamil, and on many others. It was not trained on Sanskrit. It is about 70 MB, downloaded once, and its licence is CC-BY-4.0 (source).

How it would be used

We do not ask the model to recognise Sanskrit. The verse is already known, so it is turned into the sounds it should contain, and the model is asked how clearly each syllable's sounds were heard. Each syllable is then compared with the same syllable in the reference take. That comparison matters: any sound the model always hears a little differently, even on the reference, cancels out, so what remains is a real difference between your take and the reference.

What it gets wrong

On the two clips the report examined, the model heard ś and ṣ as the same sound, and dropped the breath from dhū. Whether that holds beyond those clips is a hypothesis. Pick a syllable below to see the sounds it should contain.

Where it can run

  • On a laptop: yes. The expectation is one to two seconds for a verse, but that is a hypothesis: the speed in a browser has not been measured.
  • On a phone: plausible. The model is small enough for an iPhone's memory limit; larger models are not. The speed is not measured either.
  • If it cannot run (old browser, little memory, or you decline the download), the quick check still works on its own.

What this can and cannot tell you

It can show what the deeper check would work from. It cannot show how it performs: that is chapter 7, and only for one voice.

For the technically curious

ZIPA-small (CR-CTC 500k) has 64 million parameters (ACL 2025), licence CC-BY-4.0, and outputs 127 speech-sound symbols including retroflex, aspirated and long sounds. Sizes: 70.7 MB at 8 bits, 131.6 MB at 16, 260.3 MB at 32. It needs an 80-value audio feature that must be re-written in JavaScript and checked against the Python one. Native speed on one laptop thread: 0.042 times real time, 0.55 s for a 13.2 s verse. The verse's transliteration becomes expected sounds through a fixed table of about 40 rules; the score is the GOP drop against the reference take, and on clean takes the median drop was 1.34 nats. The sample output for Day 2 verse 1 begins hoːmmkratʃtʃaːmrakʃaːt̪umeːtaːrakaːmaruːpaːnivaːsiːni.

Runtime: onnxruntime-web 1.31.1 (MIT) on WebAssembly or WebGPU; threads need a page setting GitHub Pages lacks without a workaround (hypothesis). WebGPU (2025-11-25): Chrome and Edge 113 and later on desktop; Chrome 121 and later on Android 12 and later with some chips; Firefox 141 and later on Windows, 145 and later on Apple-silicon Macs; Safari 26 on iPhone, iPad and Mac. An iPhone page has about 300 MB reliably (WebKit 269777), so the 240 to 630 MB models are for laptops only. Browser speed is a hypothesis: 2 to 3 times slower than native.

Other models in the report: ZIPA-large (not checked; about 4.7 times small is a hypothesis; desktop only); wav2vec2-lv-60-espeak (317.7 MB, Apache-2.0, desktop only); speako (355.2 MB, English sounds only, rejected); vakyansh Sanskrit (377.8 MB, no licence stated, blocked); MMS_FA and Whisper tiny (rejected). POWSM claims parity with ZIPA; its size was not checked. Source for all of this: report 1, sections 3 and 4.
