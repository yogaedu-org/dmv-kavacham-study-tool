Where the audio lives

The reference clips have to come from somewhere, and the page must say clearly where it looked when it finds nothing. The design is one swappable source, so changing where the audio lives never means changing the player.

Three places, tried in this order

  1. Your own files. Clips you picked on this device and the browser keeps for you.
  2. A copy on the device (called offline). A copy saved earlier, so the verse plays with no network.
  3. The cloud. The same website the app is served from.

If none of them has the verse, the page says "No audio for verse N" and names what it tried, and the play button is disabled. It never fails silently.

Why the cloud is the app's own website

A set of clips for one day is 14 files and about 3 MB. Hosting them on the same GitHub Pages site as the app costs nothing and the page can read and analyse them, because they come from the same place. GitHub allows 1 GB per Pages site and a soft limit of 100 GB of downloads a month, which is about 34,000 full downloads of a day set (a calculation from the 2.9 MB set size).

Files attached to a GitHub release cannot do this job. They carry no permission header (CORS), so the page may play them but not analyse them, and a draft release answers "not found" to the public. Cloudflare R2 is possible, costs nothing at this size, but its test address is rate-limited and a real one needs a custom domain.

Source: report 2, answer and section 1 (fetched 2026-11-12), including GitHub Pages limits and R2 public buckets.

Offline, and the iPhone catch

The design is a button, "Download Day 3 (2.9 MB)", that fetches the clips, checks each against its fingerprint (SHA-256) and stores them in the browser's cache so they play with no network. On an iPhone, Safari deletes a site's stored data, including this, after 7 days without a visit, unless the app is added to the Home Screen. Whether that is still exact in iOS 26 was not checked (hypothesis). So the page should say "Add to Home Screen to keep offline audio" next to the download.

On this test site, "offline" is only a folder of clips beside the page (local-audio/), filled by a copy script. The download button and the service-worker design are in the report and are not built here.

Source: report 2, section 3, citing WebKit, 2020-03-24.

Your own files

A file picker works in every browser, an iPhone included, and the page copies the bytes into its own storage. A folder picker only exists in Chrome and Edge 105 and later, so it is not relied on. Files are matched to verses by the number in the name: verse-07.mp3 is verse 7. If a name has no number, the page asks which verse it is.

Source: report 2, section 4, citing caniuse.

Format

MP3, mono, constant bitrate. Every major browser plays it. At 128 kilobits per second a 12 second clip is about 192 KB. Constant bitrate keeps a jump to a syllable exact; a variable bitrate file may drift (hypothesis). Halving to 64 kilobits would halve the set, but needs a listening check first (hypothesis).

Source: report 2, section 5, citing MDN audio codecs.

What this can and cannot tell you

It shows how a clip is found and what the error says when it is not. It does not show offline storage on a phone or the cloud copy, because neither is set up on this test site. The ribbon always uses the reference's syllable moments, so with your own file it only follows the sound approximately.
